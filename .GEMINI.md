# Global Antigravity Rules for Gemini Agent

This file defines cross-workspace baseline behavior for the Gemini agent. All repositories inherit these rules unless explicitly overridden by local `GEMINI.md` or `AGENTS.md` files.

**Purpose**: Establish consistent agent behavior, coding standards, and decision-making protocols across all workspaces.

**Scope**: Global baseline rules that apply unless local workspace rules override them.

**Version**: 1.1.0
**Last Updated**: 2025-01-06
**Status**: Active

## 1. Workspace Hierarchy & Precedence

### 1.1 Precedence Order (Highest to Lowest)

1. **Local `AGENTS.md`** — Project-specific agent policy and conventions
2. **Local `GEMINI.md`** — Project-specific Gemini rules and overrides
3. **Local `.amazonq/rules/`** — Amazon Q-specific rules (if present)
4. **This file** — `~/.gemini/GEMINI.md` (global baseline)

### 1.2 Conflict Resolution Protocol

**Rule**: Local rules ALWAYS override global rules.

**Process**:

1. **Read local files first**: Check for `AGENTS.md`, `GEMINI.md`, `.amazonq/rules/` in workspace root
2. **Identify conflicts**: Compare local rules with global rules
3. **Apply precedence**: Use local rule if conflict exists
4. **Document decision**: Quote the source rule when explaining behavior
5. **Ask if unclear**: Request user clarification if rules are ambiguous

**Example**:

```text
Global rule: "Use 4 spaces for indentation"
Local rule: "Use 2 spaces for indentation"
Result: Use 2 spaces (local wins)
```

## 2. Core Principles

### 2.1 Confirmation Before Action

**Protocol**: Read → Understand → Confirm → Act

**Steps**:

1. **Read local rules**: Check `AGENTS.md`, `GEMINI.md`, `.amazonq/rules/` before ANY code changes
2. **Understand context**: Review sibling files to understand existing patterns
3. **Confirm approach**: If uncertain, ask user before proceeding
4. **Quote evidence**: Reference specific rules/files when explaining decisions
5. **Document changes**: Note which rules guided your implementation

**Example Confirmation**:

```text
User: "Add a new controller"
Agent: "I see the project uses Laravel 12. According to AGENTS.md,
I should use 'php artisan make:controller --resource'.
Should I proceed with this approach?"
```

**Never Assume**:

- ❌ "I'll use my default approach"
- ✅ "I'll check the project's conventions first"

### 2.2 Respect Project Conventions

**Discovery Process**:

1. **Check package files**: `package.json`, `composer.json`, `pyproject.toml`, `Makefile`
2. **Read scripts section**: Identify available commands (`dev`, `build`, `test`, etc.)
3. **Review sibling files**: Match naming, structure, and patterns
4. **Follow existing style**: Indentation, quotes, line length, etc.
5. **Use project tools**: Don't introduce new tools without approval

**Command Discovery Priority**:

```text
1. Check package.json "scripts" section
2. Check composer.json "scripts" section
3. Check Makefile targets
4. Check README.md for documented commands
5. Check AGENTS.md or GEMINI.md for project-specific commands
6. Ask user if no commands found
```

**Pattern Matching Examples**:

```php
// Existing file uses constructor property promotion
public function __construct(
    private UserService $userService
) {}

// Your new code should match this pattern
public function __construct(
    private AssetService $assetService
) {}
```

**Never Invent**:

- ❌ New build tools (e.g., introducing Webpack when project uses Vite)
- ❌ New test frameworks (e.g., introducing Jest when project uses PHPUnit)
- ❌ New code formatters (e.g., introducing Prettier when project uses Pint)
- ❌ New architectural patterns (e.g., introducing repositories when project uses services)

### 2.3 Protect Guarded Directories

**Critical Rule**: NEVER modify these directories without explicit user approval.

#### 2.3.1 Dependency Directories (NEVER TOUCH)

- `vendor/` — PHP dependencies (managed by Composer)
- `node_modules/` — JavaScript dependencies (managed by npm/yarn)
- `.venv/`, `venv/` — Python virtual environments
- `packages/` — Go modules cache

**Instead**: Use package managers (`composer install`, `npm install`, etc.)

#### 2.3.2 Runtime & Cache Directories (READ-ONLY)

- `storage/` — Laravel runtime data, logs, cache
- `bootstrap/cache/` — Laravel application cache
- `var/cache/` — Symfony cache
- `.cache/` — Generic cache directories
- `tmp/`, `temp/` — Temporary files

**Instead**: Use framework commands (`php artisan cache:clear`, etc.)

#### 2.3.3 Build Artifacts (REGENERATE, DON'T EDIT)

- `dist/`, `build/`, `out/` — Compiled output
- `public/build/` — Vite build output
- `public/hot` — Vite dev server indicator
- `.next/` — Next.js build cache

**Instead**: Run build commands (`npm run build`, `composer run build`, etc.)

#### 2.3.4 Configuration & Secrets (ASK FIRST)

- `.env`, `.env.local`, `.env.production` — Environment variables
- `secrets/`, `.secrets/` — Secret management
- `.kiro/`, `.agents/` — Agent configuration
- `config/secrets.yml` — Symfony secrets
- `.aws/`, `.azure/` — Cloud credentials

**Protocol**: Always ask user before modifying. Never commit secrets.

#### 2.3.5 Version Control Metadata (NEVER TOUCH)

- `.git/` — Git repository data
- `.svn/` — Subversion data
- `.hg/` — Mercurial data

**Instead**: Use git commands (`git add`, `git commit`, etc.)

### 2.4 Concise & Factual Communication

**Communication Style**: Brief, factual, evidence-based.

#### 2.4.1 Response Structure

**Format**:

1. **Direct answer** (1-2 sentences)
2. **Evidence** (quote from code/docs if relevant)
3. **Action** (what you'll do or need)
4. **Confirmation** (ask if uncertain)

**Example (Good)**:

```text
User: "How do I run tests?"
Agent: "Run 'composer test' (defined in composer.json scripts).
This executes PHPUnit with the project's configuration.
Should I run the tests now?"
```

**Example (Bad - Too Verbose)**:

```text
User: "How do I run tests?"
Agent: "Well, there are many ways to run tests in PHP projects.
You could use PHPUnit directly, or you might have a composer script.
Let me explain the history of PHP testing frameworks..."
```

#### 2.4.2 Evidence-Based Claims

**Always quote sources**:

- ✅ "According to AGENTS.md line 45, use PSR-12 formatting"
- ✅ "The sibling file UserController.php uses constructor injection"
- ✅ "composer.json defines 'test' script as 'phpunit'"
- ❌ "I think the project uses PSR-12" (no evidence)

### 3.1 Build & Test Commands

**Step-by-step**:

   - `pyproject.toml` → `[tool.poetry.scripts]` or `[project.scripts]`

### 3.2 Code Quality Standards

#### 3.2.1 Pre-Commit Checklist

**ALWAYS run before finalizing changes**:

1. **Format code**: Run project formatter
   - PHP: `vendor/bin/pint --dirty`
   - JavaScript: `npm run format` or `prettier --write`
   - Python: `black .` or `autopep8`
   - Go: `go fmt ./...`

2. **Lint code**: Check for errors
   - PHP: `vendor/bin/phpstan analyse`
   - JavaScript: `npm run lint` or `eslint`
   - Python: `flake8` or `pylint`
   - Go: `golangci-lint run`

3. **Run tests**: Ensure nothing breaks
   - `composer test` or `php artisan test`
   - `npm run test`
   - `pytest`
   - `go test ./...`

4. **Check types**: If using type systems
   - TypeScript: `npm run type-check` or `tsc --noEmit`
   - Python: `mypy .`
   - PHP: `vendor/bin/phpstan` (already covered in lint)

5. **Review changes**: Use git diff
   - `git diff` — Review unstaged changes
   - `git diff --staged` — Review staged changes

#### 3.2.2 Commit Message Standards

**Format**: `<type>(<scope>): <subject>`

**Types**:

- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation changes
- `style`: Code style changes (formatting, no logic change)
- `refactor`: Code refactoring (no feature/bug change)
- `test`: Adding or updating tests
- `chore`: Maintenance tasks (dependencies, build, etc.)

**Examples**:

```text
feat(auth): add two-factor authentication
fix(helpdesk): resolve ticket assignment bug #123
docs(readme): update installation instructions
refactor(services): extract notification logic to service class
test(loan): add tests for loan approval workflow
chore(deps): update Laravel to 12.1.0
```

### 3.3 File Operations

#### 3.3.1 Reading Files

**Tool**: `fsRead`

**Best Practices**:

- **Batch reads**: Read multiple files in one call when possible
- **Check truncation**: If `truncated=true`, file exceeds 200K chars
- **Read context**: Read sibling files to understand patterns
- **Read before write**: Always read existing file before modifying

#### 3.3.2 Creating Files

**Tool**: `fsWrite` with `command: "create"`

**Best Practices**:

- **Check if exists**: Don't overwrite existing files without confirmation
- **Create parent dirs**: Ensure parent directories exist (tool doesn't auto-create)
- **Follow conventions**: Match naming and structure of sibling files
- **Add file header**: Include appropriate file headers (license, namespace, etc.)

#### 3.3.3 Modifying Files

**Tool**: `fsReplace`

**Best Practices**:

- **Batch changes**: Use multiple `oldStr`/`newStr` pairs in one call
- **Exact matching**: `oldStr` must match EXACTLY (including whitespace)
- **Include context**: Include surrounding lines for uniqueness
- **Minimal changes**: Only include lines that change, plus context

#### 3.3.4 Deleting Files

**Protocol**:

1. **Ask first**: "Should I delete [file]? This cannot be undone."
2. **Explain impact**: "This file is used by [components]. Deleting it will break [functionality]."
3. **Suggest alternatives**: Archive, comment out, or deprecate instead
4. **Wait for confirmation**: Don't delete until user explicitly approves

## 4. Language-Specific Rules

### 4.1 PHP/Laravel

- Always use `declare(strict_types=1);` at file start
- Use explicit type hints for all parameters and return types
- Use constructor property promotion (PHP 8+)
- Run `vendor/bin/pint --dirty` before committing
- Run `vendor/bin/phpstan analyse` for static analysis
- Use `php artisan make:*` commands to generate files
- Never use `env()` outside `config/` files; use `config()` instead

### 4.2 JavaScript/TypeScript

- Use `npm run build` to compile frontend assets
- Use `npm run dev` for development with hot reload
- Follow ESLint/Prettier rules defined in `.eslintrc` and `.prettierrc`
- Use TypeScript for type safety when available
- Test with `npm run test` or project-specific test runner

### 4.3 Python

- Use `pytest` for testing
- Follow PEP 8 style guide (use `black` or `autopep8` for formatting)
- Use type hints for function signatures
- Use virtual environments (`venv` or `poetry`)

### 4.4 Database/SQL

- Use ORM methods (Eloquent, SQLAlchemy) instead of raw SQL when possible
- Always include rollback logic in migrations
- Test migrations locally before committing
- Never modify production data without explicit user approval

## 5. Security & Compliance

### 5.1 Credentials & Secrets

- **Never commit** credentials, API keys, or tokens
- Use `.env` files (gitignored) for local secrets
- Use environment variables or secret management for production
- If you find exposed credentials, alert the user immediately

### 5.2 Input Validation & Authorization

- Always validate user input before processing
- Check authorization/permissions before sensitive operations
- Use framework-provided validation (Laravel validation, etc.)
- Sanitize output to prevent XSS/injection attacks

### 5.3 Dependency Security

- Run `composer audit` or `npm audit` to check for vulnerabilities
- Update dependencies regularly but test thoroughly
- Pin versions in lock files (`composer.lock`, `package-lock.json`)

## 6. Documentation & Comments

### 6.1 Code Documentation

- Use PHPDoc blocks for PHP classes/methods
- Use JSDoc for JavaScript functions
- Include type information in documentation
- Reference requirements/issues when relevant (e.g., `@see Issue #123`)

### 6.2 Inline Comments

- Explain *why*, not *what* (code should be self-explanatory)
- Use comments for complex logic, business rules, or non-obvious decisions
- Keep comments up-to-date with code changes

### 6.3 README & Guides

- Update README if adding new features or changing setup
- Include setup instructions, build commands, and testing procedures
- Document breaking changes in CHANGELOG

## 7. Testing & Quality Assurance

### 7.1 Test Coverage

- Write tests for new features and bug fixes
- Aim for >80% code coverage on critical paths
- Use appropriate test types: unit, integration, E2E
- Run full test suite before committing: `composer test` or `npm run test`

### 7.2 Test Organization

- Group related tests in test classes/suites
- Use descriptive test names (e.g., `test_user_can_create_post`)
- Mock external dependencies (APIs, databases)
- Clean up test data after each test

### 7.3 Continuous Integration

- Ensure CI/CD pipelines pass before merging
- Check for linting, type checking, and test failures
- Review security scanning results (SAST, dependency checks)

## 8. Git & Version Control

### 8.1 Commit Practices

- Write clear, descriptive commit messages
- Reference issue numbers: `Fix #123: Description`
- Keep commits focused on single concerns
- Avoid committing debug code or temporary files

### 8.2 Branch Strategy

- Use feature branches: `feature/description`
- Use bugfix branches: `bugfix/description`
- Keep branches up-to-date with main/develop
- Delete branches after merging

### 8.3 Pull Requests

- Include description of changes and rationale
- Link related issues
- Request review from team members
- Ensure CI passes before merging

## 9. Performance & Optimization

### 9.1 Code Performance

- Avoid N+1 queries (use eager loading in ORMs)
- Cache expensive computations
- Use appropriate data structures (arrays, sets, maps)
- Profile code before optimizing

### 9.2 Frontend Performance

- Minimize bundle size (tree-shake unused code)
- Lazy-load components and routes
- Optimize images and assets
- Use CDN for static files

### 9.3 Database Performance

- Index frequently queried columns
- Use query analysis tools to identify slow queries
- Archive old data when appropriate
- Monitor query performance in production

## 10. Accessibility & Internationalization

### 10.1 Accessibility (WCAG 2.2 AA)

- Use semantic HTML
- Include ARIA labels for screen readers
- Ensure keyboard navigation works
- Maintain color contrast ratios (4.5:1 for text)
- Test with screen readers (NVDA, JAWS, VoiceOver)

### 10.2 Internationalization (i18n)

- Use translation keys instead of hardcoded strings
- Support multiple languages if required
- Use locale-aware formatting (dates, numbers, currency)
- Test with different locales

---

## 11. Error Handling & Logging

### 11.1 Error Handling

- Use try-catch blocks for expected errors
- Provide meaningful error messages to users
- Log errors with context (stack trace, user ID, request data)
- Never expose sensitive information in error messages

### 11.2 Logging

- Use structured logging (JSON format when possible)
- Include log levels: DEBUG, INFO, WARN, ERROR, CRITICAL
- Log important business events (user actions, transactions)
- Rotate logs to prevent disk space issues
